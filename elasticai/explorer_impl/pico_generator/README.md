# Pico-Generator

The Pico-Generator is a implementation the elastic-ai.Explorer Generator classes. It enables deployment and measurements of hardware metrics on the Raspberry Pi Pico.
The general setup is explained in the top-level [README.md](../../../README.md) under "Pico-Generator Dependencies" and "Set up your Raspberry Pi Pico for Deployment".

It is recommended to use the explorer.Explorer class to use the Generator. A extensive example of this is found in pico_example.py. 

However, the following is a brief explanation of the usage and implementation. 


## Adding new measurement scripts
The source code for taking measurements on the pico is given as an independent cmake project: the [pico_crosscompiler](../../../docker/code/pico_crosscompiler).
This means to add new measuring scripts, add a new build target to the project. These should follow this simple structure: 
 
```
pico_crosscompiler 
│
└───script-directory <--name this as you like
        main.cpp <-- your script
        CMakeList.txt
```
Don't forget to link the script directory as a source in this and the top-level CMakeList.txt. 
An example for this is [measure_accuracy](../../../docker/code/pico_crosscompiler/measure_accuracy). 

Registering your new source to metric either with the Explorer or with the HWManager configure `CompilerParams` and `metric_to_source` like this:

```python 
compiler_params = CompilerParams(
        library_path="./relative/path/to/pico_crosscompiler",
        image_name="picobase",
        build_context="path/to/docker-directory",
        base_dockerfile_path= "absolute/path/to/Dockerfile.picobase",
    )
metric_to_source = {
    Metric.METRIC: Path("relative/path/to/new-script-directory")
    }
```


## Structuring a measurement script
The pico_crosscompiler gives you all the necessary tools to load a model and run it on the Pico MCU. 
Firstly, load the model with the TfLiteInterpreter. The model is always given as a `extern const unsigned char model_tflite[]` in "model.h".
The necessary resolver operations are autogenerated for the current model and are always found in "resolver_ops.h".

```cpp

#include "model.h"
#include "tflite_interpreter.h"

std::unique_ptr<tflite::MicroMutableOpResolver<11>> resolver(new tflite::MicroMutableOpResolver<11>());
#if __has_include("resolver_ops.h")
#include "resolver_ops.h"
#endif
std::unique_ptr<TfLiteInterpreter> interpreter(new TfLiteInterpreter(model_tflite, *resolver, TENSOR_ARENA_SIZE));
interpreter->initialize();
```

Then inference can be called like this:

```cpp
int inference_result = interpreter->runInference(inputBuffer, outputBuffer);
```

After testing the model in someway, the result should be printed in a Json format with the following structure {"metric_name": {"value": value, "unit": unit}}

Example: 
```cpp
printf(
    "{\"Accuracy\": { \"value\":  %.3f, \"unit\": \"percent\"}}", accuracy_in_percent);
```

## Deploying Test Data
Test data that should be available on runtime has to be given as an c-array of data points in one or multiple header files, that is directly compiled with the rest of the sources.
An example for this is [setup_mnist_for_cpp in utils.py](utils.py). Place all your header files in one directory and set it as the deployable dataset path in the DatasetSpecification. It will be copied to the "data"-directory when PicoHWManager.prepare_dataset(...) and can be accessed by the measurement script at runtime. 


```python
DatasetSpecification(
        dataset=YourDataset(root="path/to/test_data", transform=transf),
        deployable_dataset_path="path/to/test_data_header_directory",
    )
```

## Docker-Compiling
The PicoCompiler uses docker buildx to cross-compile for the Pico. This is done by layering two docker images. One is the base image which simulates the runtime environment of a RPi and installs all necessary build tool, this is only created one time. The smaller cross-compile image is build on top of the base image and compiles the measurement script on creation. We recommend using Dockerfile.picobase and Dockerfile.picocross respectively. These are found in the [docker directory](../../../docker) and can be specified in CompilerParams. The resulting executables are copied to a bin directory in the build context ("build-context/bin").


## Quantization
The RPi Generator currently does support full precision and int8 uniform quantization. 

To search for quantized model you can add the following to your "search-space.yaml". 
```
quantization:
  dtype: ["int8"]
```

## Using ModelTranslator individually 
The ModelTranslator can also be used individually to translate a torch model and its weight to tflite-model and c++-array in a ".cpp" file. 
The ModelTranslator uses ai_edge_torch (now torch-litert) to convert the model. The converter is still a Beta release and may return broken models or models that differ in inference results. In that case a warning is given. In practice most simple torch models are converted correctly. 
It is also able to do Post Training Quantization (PTQ). 

Example:

```python
scheme = QuantizationScheme(dtype="int8") # <-- or dtype="float16" 
tflite_translator = TFliteModelTranslator()
tflite_translator.translate(model = your_model, output_path= Path("path/to/some/output-dir"), sample=example_data_sample, quantization_scheme = scheme) # quantization_scheme=None results in a full precision model
```
